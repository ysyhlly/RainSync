# Static HLS: pending-parent custody slice

Status: implementation proposal for independent review. Base `db19f149890a41b13ef781c938051acb369d6976`; its pure contracts are being independently reviewed and corrected by a separate integration owner. This slice does not edit those files. Public fallback, prepare dispatch, RPC, reader advertisement and production activation remain off. PostgreSQL execution remains paused.

## Deliverable and exclusions

Implement one complete storage lifetime: immutable pending parent request and preparation → bounded capture admission → verified inventory → cancellation/failure → positive disposal → retained history and eventually ordered pruning. This closes the need for an already-published grant before qualification. It does not create a provisional grant.

Every request carrying this slice's non-null input is forbidden from becoming `completed`, inserting/updating a `playback_sessions` row for its session ID, or acquiring a media job. This prohibition applies before a capture exists and after its disposal. Only `stage_a` and `pending_parent` publication phases exist. Published phases, child claims/references, output recipes, RPC challenges and public markers wait for their consuming transactions in later slices. No queued media work is introduced here.

Existing Stage A/legacy rows keep their existing behavior except that the new restrictive request foreign key requires retaining any request still referenced by capture, including disposed Stage A capture. This retention change is explicit. No old source, login, Worker ownership or input facts are inferred/backfilled.

## Schema and provenance

Retarget capture `session_id` from `playback_sessions(id)` to the already-unique `playback_requests(session_id)` with an immediate restrictive FK, never a cascade. Before replacing it, validate every existing capture/request association. Missing or conflicting history aborts migration; do not fabricate a request for a disposed capture. Current 0043 permits disposed custody to outlive a pruned request, so this is a real migration prerequisite. Retargeting must also preserve the old session-FK protection for Stage A: refuse session DELETE or ID change whenever any `stage_a` capture references that original session, including unmarked/capturing and disposed captures. The current marked-session-only trigger does not cover those cases; add this explicit guard without retaining an all-phase session FK that would forbid pending-parent custody.

Add only currently consumed parent request columns: input version, bounded encrypted input, input digest, unique operation/capture ID, original root expiry and preparation expiry. Add immutable nonsecret mirrors for media ID, room media generation, source ID, source policy revision, media preview/source generation, Worker startup and database binding. The whole Stage B set is NULL for legacy or fully populated for pending-parent input. Existing request user/room/owner/login/member/viewer/generation columns remain authoritative joins, rather than duplicated fields. No source URL or configuration header becomes plaintext SQL metadata.

The input is version 1; recipe/reader facts are exactly the approved input contract. Stored ciphertext is 1–65,536 bytes; its canonical validated plaintext is at most49,124 bytes. Operation and session IDs differ. The original DB-observed admission time is retained as request `created_at`; original root is positive and no more than30 minutes later, preparation is positive and no more than45 seconds from that same first preparation start, and preparation/lease do not exceed the root. No expiry update extends these fences. SQL stores/compares exact millisecond values produced from the original DB clock sample; rounding cannot grant extra time.

Capture gains phase, input digest, Worker/database, exact reader/recipe and verification root digest. Old captures are `stage_a` with all these facts NULL. Pending-parent phase and identity never change; root digest and encrypted inventory are installed together once. Verified cannot return to capturing, and any known inventory/disposal fact is immutable. A request has at most one pending-parent capture; all `disposed_at IS NULL` rows still count toward two global/one-per-user capture capacity regardless of status, cancellation or expiry.

The Server helper derives mirrors from the same validated canonical plaintext actually encrypted and stored. It must not accept separately supplied mirror values, a caller-asserted digest, or a `validated=true` shortcut. Before locking, it may read a candidate source record and original DB clock, decrypt and construct the closed trusted input and ciphertext. Under the final ordered locks it re-reads and compares the exact source configuration ciphertext/kind, media resource/version/preview generation and source revision used for that construction, plus current room/login/member/viewer facts. Any change rejects the request rather than encrypting stale source facts. Catalog/source facts prove configuration identity only; verified graph bytes supply later resource identity.

The input builder is not a public JSON endpoint. It uses the trusted stored HTTP source and resolved catalog target. Only the parent form is admitted. Required pure input/root checks are called at their consuming boundaries, including repeated input-to-root binding on verification; a successful pure validator is never treated as live DB authority or file/process proof.

## Exact transaction and lock contract

The authority prefix is room lifecycle → room snapshot → membership → exact login → user quota → request rows → viewer high-water → source → media. Sort multiple rows consistently within each group. Source comes before media to match configuration invalidation. Recheck current clock and live authority after contended locks and in the final conditional write. Never do network, probe, file hash, decoder or physical deletion under these locks.

For any transaction needing both capture rows and budget, the suffix is **budget → capture → reservation**. Never acquire budget after holding a capture lock. Current positive disposal already uses this suffix; capture INSERT's trigger re-enters the same budget lock. The retargeted FK implicitly locks the request key, so admission must already hold its request authority lock before budget. Disposal/pruning may not acquire authority locks after budget/capture.

1. **Freeze request.** Compare key/hash and exact login before any mutation. For a new operation only, insert the fully bound pending request and preparation atomically. No session, job or token is created. An existing Stage B key returns its stable terminal/in-progress/retained-custody result; it cannot be re-owned, re-encrypted, reset or used to advance a viewer. Source construction occurs as described above, then final byte/current-fact comparison under locks
2. **Admit capture.** Authority prefix → budget → capture rows → reservation. Recheck the independently measured headroom against the unchanged budget revision, total held bytes and retained capacity. Insert pending-parent custody and exactly134,217,728 bytes of reservation atomically. Every conditional write must affect exactly one row. Mint local permit only after confirmed successful admission; uncertainty is not success or permission to reconstruct a permit from a row after restart
3. **Verify.** Authority prefix → exact request/capture. Compare request owner/session/user/input/media/source/Worker/database/deadline facts and consume the required validated root-to-parent-input check. Update inventory/root once under still-pending authority. This path has no budget lock and must not invoke a function or trigger that takes one
4. **Terminalize/cancel.** Pending → failed is stable for all reasons, including retryable transport errors. Keep the complete identity, input, deadlines and preparation/capture linkage. Verify/cancel are budget-free; cancellation cannot release storage or supply disposal proof. A permitted legacy/old-reader revocation must actually make pending authority false, not report success after silently skipping a request UPDATE
5. **Dispose.** Budget → exact capture → exact reservation. Only the original local permit plus opaque all-positive stream/process/file disposal proof acknowledges closure. No current playback/login/source authority is required to discharge an old responsibility; no room/request authority lock is taken afterward. Commit positive fields, reservation removal and budget revision together. Uncertain acknowledgment remains unresolved, with no fabricated release or blind replay that loses ownership
6. **Prune.** Room/request → budget → exact pending-parent capture → reservation/dependents. This uses the same suffix even when the reservation must already be absent; it never deletes a reservation as a pruning shortcut. Use a fresh statement/clock after locks. Require elapsed request retention, positive preparation and capture disposal, no reservation or session/job/read/output reference, no pending room cleanup, and no other retained dependency. Delete capture, then preparation/request in one ordered transaction. A terminal request for which capture was never admitted has a distinct branch: hold room/request then budget, synchronize with in-flight admission through its same request lock and obtain a fresh statement proving no capture, operation reservation or other dependency, require positive Server preparation closure and elapsed retention, then delete preparation/request. This relies on the enforced admission-before-I/O transaction and terminal request fence preventing later admission; an absent row alone never substitutes for disposal of a known or uncertainly admitted capture. If that no-admission proof is unavailable, retain the request. Preserve all Stage A capture/session/job deletion restrictions in this slice

No SQL predicate may turn reader incompatibility into source revocation. Authority joins work without reader support; cooperative reader fences govern which mutation implementations are allowed. The production pool remains reader1 and `static_hls_reader_supported()` is not broadened to accept2. Dedicated unused pending-storage transactions may establish an exact pending-only reader2/recipe1 transaction-local fence. They do not advertise or activate the full future reader2 contract. Unknown or unsupported mutations fail closed; legacy NULL rows retain their original paths.

## Existing callers that must change together

- `playback_requests::begin_authenticated`: check Stage B exact key/login/hash and terminal/custody state before retry retirement, job/upstream cancellation, session/owner replacement or viewer high-water changes. Never use existing ON CONFLICT retry semantics for a Stage B row
- Explicit cancel, newer-viewer retirement, room lifecycle and startup recovery: route the affected Stage B rows through monotonic pending→failed terminalization while preserving source/owner/history. Existing request/session/job updates must not falsely report a completed cancellation if a trigger skipped the request. No source I/O or new qualification is started by these paths
- Room cleanup's Rust blocker query and SQL room-close guard: pending capture joins through its request room, not a nonexistent playback session. Positive disposal remains independently required after cancellation
- Ordinary request housekeeping: exclude Stage B rows and any request still referenced by capture, including disposed Stage A. The request DELETE guard retains referenced rows, so an old bulk expiry pass cannot hit the new FK and roll back unrelated legacy pruning
- Preparation pruning: retain every preparation associated with a Stage B request, including requests with no capture row, until the dedicated ordered pruner proves the relevant never-admitted or positive-disposal branch and retention requirements. Generic housekeeping must exclude them even after48 hours; it cannot erase the preparation evidence first. Forty-eight hours is not a disposal proof
- `playback_requests::drained`: current code updates preparation before request; pending-parent pruning takes request first. The pending-parent acknowledgment must therefore lock the exact original request, then its preparation, and condition both writes on the original session/owner with checked row counts. Only the original executor after positive preparation closure may acknowledge. A startup/recovery path, missing row or capture status never manufactures `drained_at`. Server preparation closure and Worker capture disposal remain distinct obligations. This prevents request↔preparation inversion against pruning; retain legacy semantics where no Stage B input exists
- Generic cache budget reclamation stays `purpose='media_job'`; it never reclaims capture reservations. Existing Stage A queue/claim/normalization/cache behavior remains unchanged and cannot consume a pending-parent row

The lock review includes existing admission, positive disposal, pruning, lifecycle and all trigger-induced locks. If a required caller cannot preserve the order without broader changes, stop and report that concrete dependency instead of relaxing the invariant.
