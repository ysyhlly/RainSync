# 播放请求幂等

2026-09-30：新增可选成对 `viewer_id` / `plan_generation` 的独立方案排序；同 key 重试保持代次，新操作严格推进。旧客户端不带字段保持兼容，新 Web 必须搭配支持回显的后端。每用户每房间累计最多1024个 viewer 身份，不能以删除高水位腾出名额。完整语义、运维边界与本轮证据见 [播放方案代次](PLAYBACK_PLAN_GENERATIONS.md)。

`POST /api/v1/playback-sessions` 接受可选 `idempotency_key`（UUID）。新 Web 为一次播放操作生成一个编号，网络结果不确定时使用相同编号及相同参数重试。主动切换影片、音轨、模式或重新发起播放属于新操作，使用新编号。旧客户端省略编号仍可创建会话，但无法依靠服务端生成的内部编号进行跨请求去重。

```json
{
  "idempotency_key": "11111111-1111-4111-8111-111111111111",
  "room_id": "22222222-2222-4222-8222-222222222222",
  "media_generation": 1,
  "mode": "auto",
  "position_ms": 0
}
```

## 状态和结果

| 条件 | 结果 |
|---|---|
| 新编号通过鉴权和配额 | 先提交准备记录，再协商/探测媒体；一次只由原执行者创建会话 |
| 同一用户、编号、规范化参数，原请求成功且会话有效 | 200，复用 session_id、媒体 URL、音轨/字幕；expires_in_seconds 更新为剩余时间 |
| 同一用户和编号，房间/代次/位置/音轨/模式/能力等参数不同 | 409 `PLAYBACK_REQUEST_CONFLICT` |
| 原请求仍在准备 | 409 `PLAYBACK_REQUEST_IN_PROGRESS`，可用相同参数稍后查询 |
| 原准备已中断、执行期限已过或 owner epoch 不匹配 | 同 key 接管，停止旧授权，以新 session_id 执行下一次准备 |
| 已记录可重试失败 | 同 key 再次准备；每 key 最多三次执行，第三次可重试失败直接返回不可重试的 `PLAYBACK_REQUEST_RETRY_EXHAUSTED`，后续同 key 回放此终止结果 |
| 已记录不可重试失败 | 返回原 HTTP 状态及错误码 |
| 原会话停止、过期、媒体代次改变，或未完成记录保留期已过 | 410 `PLAYBACK_REQUEST_EXPIRED`，不复活旧授权 |
| 不同用户使用同一编号 | 独立作用域，各自仍须通过房间鉴权 |
| 请求已按 key 取消 | 410 `PLAYBACK_REQUEST_CANCELLED`，不可重试此 key |

鉴权、加入房间检查发生在查询原结果之前，不能用编号获取他人的方案。默认值归一化（例如省略 mode 与 auto 相同）；请求内容摘要覆盖完整类型化参数，不只比较动作名称。没有通过鉴权/配额、尚未取得准备记录的请求不产生媒体副作用。

## 事务与恢复

迁移 `0003_playback_requests.sql` 增加请求记录，不修改已部署迁移。短事务对用户行加锁，串行检查活跃会话与待处理请求的合并数量；每用户上限由 `PLAYBACK_SESSION_LIMIT` 配置，默认 2，原有八路部署可显式设为 8。探测会话与准备记录使用同一 session_id，因此只计一次。网络协商期间不持有这把锁，也不占用长事务。媒体任务还受全局入队限制，详见 [容量说明](MEDIA_CAPACITY.md)。

成功方案、最终播放会话、媒体任务在同一事务中提交。方案含播放票据，使用站点密钥加密保存；明文只保存请求摘要和状态。数据库备份必须继续配套保存 SOURCE_ENCRYPTION_KEY。提交确认丢失时，失败处理先查看是否已经成功提交，不能覆盖成功记录或撤销已完成方案。

准备操作最多执行 45 秒；准备记录的执行期限为 60 秒，最终提交必须仍由原实例、原 session_id 持有且未过期。迁移 `0004_playback_request_attempt.sql` 记录执行次数，每 key 最多三次。接管事务撤销旧会话、取消旧媒体任务并分配新 session_id；探测授权插入和最终方案提交都检查并锁住当前请求，旧执行者晚到的成功或失败不能覆盖新执行者。失败会撤销尚存的探测授权。Server 取得单实例锁后将上次进程遗留的 pending 标为可重试中断，并撤销其准备授权。

鉴权后，预留事务、准备和失败收尾由独立 Tokio 任务持有；从 begin 之前开始转移所有权，避免预留已提交、HTTP waiter 被丢弃时遗留无人执行的 pending。HTTP 断开或单次 fetch 超时不会取消这项任务：成功保存方案供同 key 重放，失败立即记录并停止探测授权，45 秒准备截止仍执行失败收尾。主动放弃使用 DELETE 取消接口，取消记录阻止任务晚到提交。进程崩溃或数据库不可用仍依赖既有启动恢复/租约机制。

重试可能重新协商上游。上游服务自己的资源终止/重试完整矩阵仍属 W03；本地会话去重不能保证进程崩溃前已发出的上游副作用恰好执行一次。

记录至少保留 48 小时；播放续期在同一事务中将记录保留期延长至至少当前时间后 48 小时。已完成记录优先检查真实会话是否有效，即使记录保留时间已到，仍可取得有效方案并延长记录保留时间。清理不得删除仍有有效播放会话的记录。保留窗口以外不承诺永久去重，因此客户端永远不回收旧操作编号用于新操作。

新 Web 每次 HTTP 尝试有 65 秒预算；网络失败、单次 HTTP 超时和 200 响应正文截断共用三次传输失败上限，可重试准备错误另有三次上限，二者互不扣减。服务端实际执行次数仍由同 key 最多三次的计数决定，收到 RETRY_EXHAUSTED 立即停止。整段操作硬上限为 335 秒（包含准备中轮询），可容纳两次不确定传输等待及三次完整 HTTP 尝试，再加四次 1 秒重试间隔（329 秒）。始终复用编号及参数；鉴权、参数及不可重试准备失败直接展示。

主动切换或停止产生独立的 PlaybackCancelled（播放准备已取消），不作为用户可见失败；真正到达请求/操作截止才产生 PlaybackTimeout。重试间隔也可立即取消。旧加载、旧 UI 操作及旧媒体回调不能改写新操作的错误或忙碌状态，tick、元数据回调和页面唤醒引起的准备都有 rejection 处理。完整生命周期验收仍由 W06 补齐。

## 放弃请求与释放配额

`DELETE /api/v1/playback-requests/{key}` 使用登录用户作用域及 CSRF 校验。它在短事务中保存不可重试的取消记录、停止对应播放会话并取消 queued/running 任务；重复取消成功。取消先于首次 POST 到达时也会保存记录，阻止晚到 POST 创建会话。准备已在执行时，现有 guard 阻止晚到结果提交。取消别人的相同 key 不会影响别人的会话。取消记录至少保留 48 小时。

网页每次准备开始前保存 key；一次操作内部的瞬时失败仍用相同 key 重试。自动重试预算用尽、超时、停止或切换后，按 key 明确取消该操作，无需先知道 session_id。取消确认后才可换新 key；取消失败保留 key，并阻止继续创建占用配额的新请求，提示恢复连接后重试。用户作用域的 key 列表保存在 sessionStorage，同一标签页刷新后先处理遗留清理；其中不含媒体 URL 或票据。断网期间不能保证立即撤销服务端授权，彻底关闭标签页后的存储恢复和完整后台回收仍非本次已验证范围。

部署这版网页前，后端必须已支持取消接口，或将两者一起更新；不能把依赖取消确认的新版网页单独搭配旧后端使用。

验证入口：`node tests/integration.mjs`（调用 `tests/playback-idempotency.mjs`）、`npm test`、`npm run test:e2e`。真实数据库覆盖并发、加密结果复用、事务回滚、过期接管和进程重启；受控上游验证成功重放只协商一次、瞬时失败后同 key 恢复及旧任务晚到不覆盖新结果；浏览器测试验证断流/截断 JSON/准备中之后仍复用原编号，不充当真实媒体解码验收。`cargo run -p protocol --example export -- --check` 无写入核对 TS 和 JSON Schema 是否与 Rust 一致，已纳入 CI。
