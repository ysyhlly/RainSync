# 控制命令有效期与重放

控制命令需要服务端签发的 `control_epoch`。它与进程时钟 `clock_epoch`、影片 `media_generation` 分别解决不同问题，不能互相替代。

加入/恢复房间时，SNAPSHOT 顶层包含：

```json
{
  "control_epoch": {
    "id": "11111111-1111-4111-8111-111111111111",
    "expires_at_ms": 1790553600000
  }
}
```

新控制命令携带 `control_epoch.id` 作为字符串字段，另生成新的 `command_id`。服务端记录凭据所属用户、房间、签发时间和有效期；数据库约束最长 24 小时。有效期使用数据库时间，网页无需依赖本地时钟判断授权。凭据只约束命令生命周期，不代替登录、成员和控制者权限检查，也不授予观看者控制权。

## 校验顺序

1. 检查套接字房间与命令房间一致。
2. 检查控制凭据存在、用户/房间匹配且未过期，再查询去重结果。
3. 重放必须匹配用户与完整规范化命令；同 ID 不同参数拒绝。
4. 新命令计算下一状态，在最终事务取得快照行锁后再次检查凭据有效期；排队期间过期不会落库。
5. 快照、事件、命令结果在原有事务内提交。

缺少字段返回 `CONTROL_EPOCH_REQUIRED`；未知、跨用户/房间或过期凭据返回 `CONTROL_EPOCH_EXPIRED`。两者不可自动重试旧命令。ERROR 包含当前状态，服务端成功签发新凭据时同时附带新的 `control_epoch`；网页只更新状态和凭据，等待用户重新操作并生成新 command_id。更新凭据不会关闭观看连接。签发暂时失败时可重新连接获取新快照。

成功的去重记录也不能绕过凭据过期检查。即使旧结果已被清理，只要原凭据已过期，旧命令也不会作为新命令执行。

## 保留与重启

- 房间事件仍保留 24 小时，用于增量恢复。
- 命令去重结果保留 48 小时，独立于事件清理。
- 控制凭据最长 24 小时，过期后清理。凭据持久化到数据库，进程重启不让仍有效的凭据失效。
- 原命令在有效期内重放仍匹配原参数；如果进程时钟已变，ACK 返回当前状态而不是旧时钟的状态，不再次执行动作。

后台调用 `persistence::cleanup_control_history`。运维或隔离测试也可在明确设置目标 DATABASE_URL 后运行 `cargo run -p persistence --example cleanup_control_history`；该命令删除过期控制凭据及超过 48 小时的命令结果，不要把它误指向未知数据库。

## 兼容与验证

这是 alpha 控制接口的行为变更。Rust/Schema 允许解码缺失字段，以便旧客户端得到明确的同步错误；旧客户端不能继续执行不带凭据的控制命令。部署时配套更新后端和网页，并刷新旧页面；观看和聊天消息不增加此字段。已有旧命令结果不能在新凭据下自动重发。

新增迁移 `0006_control_epochs.sql`，TS 与 command/control-epoch/error-response Schema 从 Rust 导出。测试入口为 `node tests/integration.mjs`（含 `tests/control-epochs.mjs`）和 `npm run test:e2e`。前者验证用户/房间作用域、未知/缺失凭据、过期成功重放、删除旧结果后仍拒绝、事务锁等待中的过期、重启及真实清理函数的 25/49 小时边界；后者验证网页不会重发旧命令，下一次操作携带新凭据和新 ID。
