## 1. 用户已确认

- 管理员生成注册邀请码，用户先填写邀请码，再设置登录账号、可选昵称、密码和确认密码。
- 一码一人；只有注册成功才消耗邀请码；支持批量生成。
- 有效期默认 7 天，生成时可选 1 天、7 天或 30 天。
- 首版不收集邮箱、手机号，也不增加邮箱验证。
- 登录账号唯一、注册后不可更改，只允许英文字母、数字、下划线 _、短横线 -、点 .。
- 昵称允许中文、Emoji 和重名，最多 50 个字符，可随时修改；注册时可选填，未填默认使用登录账号。
- 密码至少 8 个字符，允许英文字母、数字、英文符号和空格，不允许中文。
- 个人资料可设置静态头像：JPG/PNG/WebP，长方形可调整裁剪，保存512×512；参考开源项目仅限思路，裁剪/上传逻辑独立实现。
- 注册成功后自动登录，进入放映室列表；新账号只有普通用户权限。
- 前端设计必须同步加入这部分，继续使用主色 #E5D1C1、辅色 #9E7867、浅色主题、纯文字 RainSync 品牌及无情绪标语的文案。
- 当前仍只做设计和 Plan，不修改项目源码。工作包在“杂项”独立 Git 留档，用户后续自行处理 GitHub。

## 2. 功能边界与现有实现

当前只有管理员 POST /api/v1/users 创建普通账号，没有自助注册接口。现有 invites 表和 rooms/{id}/invites 接口只负责加入放映室，不能拿来直接注册账号。

| 事项 | 注册邀请码 | 房间邀请 |
|---|---|---|
| 用途 | 创建一个普通账号 | 把已有账号加入指定房间 |
| 发起人 | 管理员 | 当前房间控制者或已有成员资格的管理员 |
| 使用前 | 无需登录 | 必须登录 |
| 次数 | 一次，成功注册后消耗 | 沿用现有房间规则 |
| 有效期 | 1 / 7 / 30 天 | 沿用当前 24 小时 |
| 成功结果 | 账号 + 登录会话 | 房间成员资格 |

注册不会自动加入邀请者的房间，也不会创建好友关系或群组。普通用户沿用现有权限：可以创建房间、查看站点共享媒体库，播放仍要满足房间成员等服务端要求。注册邀请码只控制开户，不承担逐人分配片源的功能。

保留现有管理员手动创建账号入口作为次级功能，与注册共用新账号规则；新增本人修改昵称的个人资料页。不引入完整账号列表、禁用、密码重置、邮箱找回、审批或自动发送邀请。管理员通过复制把邀请码交给用户，系统不代发消息。

## 3. 用户端页面与交互

### 路由与入口

- /login：原登录表单下增加“使用邀请码注册”文字入口。
- /register：无需登录可访问，只有两个步骤，不让用户在多个页面间反复跳转。
- /account/profile：已登录的个人资料页，昵称与头像分别编辑，只读展示登录账号。
- 已登录用户访问 /register 时返回 /rooms；不为了注册另一账号自动退出当前观看会话。
- 注册成功固定进入 /rooms。房间为空时显示“还没有加入放映室”，提供“创建放映室”和“通过邀请加入”。
- 登录页面不出现假的“忘记密码”入口；注册完成也不暗示已有邮箱找回能力。

### 第一步：验证邀请码

标题“创建账号”，步骤“1 验证邀请码 / 2 设置账号”。仅有一个带明确 label 的“邀请码”输入框，允许粘贴完整代码；帮助文字“邀请码由管理员提供”，主要按钮“继续”，底部“已有账号？登录”。

前端先做空值/格式检查，再按点击或回车验证；不在每次按键时调用接口。验证中仅禁用当前提交按钮。校验成功显示“邀请码已验证”，进入第二步。校验不消耗、不预留邀请码；最终提交仍须重新校验。

错误码不存在、已过期、已使用和已撤销时，未登录页面统一提示“邀请码无效或已失效，请检查后重试或联系管理员”。不透露使用者、管理员姓名或历史记录。网络错误独立提示，可重新验证。

### 第二步：设置账号

顶部保留两步进度，展示“邀请码已验证”和尾号，以及“更换”操作。表单依次为“登录账号 / 昵称（可选）/ 密码 / 确认密码”。主按钮“创建账号”，提交中“正在创建…”。登录页也统一将原“用户名”标签改为“登录账号”，不接受昵称登录。

建议的字段规范：

| 字段 | 规则 |
|---|---|
| 登录账号 | 必填；建议沿用现有长度 1–80，全部是 ASCII；完整匹配 [A-Za-z0-9_.-]{1,80}，不接受空格、中文和其他标点 |
| 唯一性与不可变 | username 存储字段继续作为登录账号，保持当前精确、区分大小写的唯一性并在表单注明；一经创建，个人资料和管理员操作均不能更改；服务器拒绝修改字段 |
| 昵称 | 可选，支持中文、Emoji、数字及符号；允许重名；不超过 50 个 Unicode 码点（前端 Array.from，后端 chars 计数）；组合 Emoji 可能计多个码点；空值或纯空白时使用登录账号作为显示默认值 |
| 密码 | 所有新建账号至少 8、最多 1024 个 ASCII 可打印字符；范围 U+0020–U+007E，包含英文空格，不含中文、全角文字、Emoji、制表或换行；不强制字符种类混合 |
| 密码处理 | 不 trim、不自动转大小写、不偷偷规范化；允许粘贴和密码管理器；默认隐藏，可按按钮显示 |
| 确认密码 | 前端必须与密码一致；不作为第二份密码发送后端 |

当前创建接口的下限仍为 12 字节。未来将新注册、管理员手动创建和空数据库管理员初始化统一为上述新账号/密码规则；既有账号登录只验证原凭据，不新增字符白名单或最小长度检查，不使历史账号失效。不会自动修改已有密码和登录账号。

登录账号占用时定位到该输入，保留其他当前输入，不消耗邀请码；昵称重复完全合法。没有单独的匿名登录账号查询接口，只有有效邀请码提交注册后才反馈占用。

密码只存在当前表单内存和提交请求中；不进入路由、Pinia 持久化、localStorage/sessionStorage、日志或错误分析。成功或离开注册页时清空敏感字段。昵称按普通文本渲染，绝不用 v-html 或 Markdown 执行其中内容；允许输入符号并不意味着执行 HTML。

### 个人资料与昵称展示

点击登录后的左侧用户区进入“个人资料”（/account/profile）。头像区支持上传/更换/恢复默认，独立裁剪弹窗见头像专项。显示只读登录账号和“登录账号不可修改”，编辑昵称、显示 0–50 字符计数，按钮“保存昵称”。昵称和头像分别保存；没有可编辑的登录账号输入和“修改账号”按钮，不在这里放尚未实现的密码修改入口。

保存成功更新本机 session store 中 display_name，侧栏和后续消息显示昵称；失败保留输入。清空昵称恢复默认登录账号。50字符上限针对用户自行设置的昵称；登录账号作为默认显示时保留原值（可能超过50），不擅自截断保存，界面用省略/换行处理。资料表单读取 custom_display_name：没有自定义昵称时输入为空，以登录账号作占位提示，避免把80位历史账号当成超限昵称提交。本人页面、普通管理员账号均可修改自己的昵称，不能通过该接口替他人修改。

房间聊天的历史接口和新消息广播都增加 user_id、display_name，保留既有 username 字段表示登录账号以兼容旧客户端。新界面主文只显示 display_name；权限判断始终基于 user_id，不依赖可重名昵称。管理员邀请码使用记录同时显示昵称和登录账号，便于确定使用者。

首版不增加全站昵称变更广播：改名后本人界面即时更新，新发送的消息和重新加载的聊天历史使用最新昵称；其他客户端已经显示的历史消息可以保留当时的显示名称，刷新后统一。该边界不得被宣传为全站历史文字实时更新。

资料页属于登录后的应用外壳，进入资料页或保存昵称时继续迷你播放，不断开连接、不重新创建播放会话。

### 成功及异常结果

- 成功：后端一次提交账号、邀请码消费记录和登录会话；返回身份/CSRF，设置现有 HttpOnly Cookie。前端填充 session store，短暂提示“注册成功”，直接到 /rooms，不为动画延迟跳转。
- 在填写期间邀请码被他人使用或被撤销：提交失败，提示更换邀请码；不建立半成品账号，不自动拿另一个邀请码重试。
- 数据库明确回滚：展示可重试错误；邀请码仍未使用。
- 超时、响应中断或未知的 5xx：显示“暂时无法确认注册结果”，不写成“注册失败”并自动重发。先通过 /auth/me 尝试确认本次用户名是否已经登录；若无法确认，提供带用户名的“前往登录”，用户可用刚设置的密码登录。请求还未结束时再次登录失败也不证明账号未创建，保留等待重试提示。
- 若 /auth/me 返回其他身份，停止本次注册流程并明确显示该身份，不把它当成本次注册成功。
- 账号已创建但 Cookie 被浏览器阻止：明确说明账号已创建，跳转登录排查；不再次消耗邀请码或创建重复账号。

## 4. 管理端页面与交互

### 入口、列表与权限

左侧管理导航将原“创建账户”扩展为“账号与注册”。默认进入 /admin/registration-invites；页内标签为“注册邀请码”和“手动创建账号”，后者仍使用 /admin/users。普通用户不显示该导航，服务端同时检查管理员权限。

列表字段：邀请码尾号、备注、状态、创建时间、有效期至、使用者、使用时间、操作。窄桌面可把时间放到次行，移动改为信息卡；记录很多时用游标分页，不加载全表。筛选“全部 / 未使用 / 已使用 / 已过期 / 已撤销”，提供刷新。不把当前页条数当全站总量。

历史列表只显示尾号，不提供复制完整代码的按钮。首次空态为“暂无注册邀请码”及“生成邀请码”；加载失败保留刷新入口，不能冒充空列表。

### 生成抽屉

桌面右侧约 400–440px 抽屉；移动为底部全宽面板，可滚动且按钮不被键盘遮挡。

- 数量：默认 1，建议每批 1–50 个；数字输入和加减都可用。
- 有效期：分段选项 1 天 / 7 天 / 30 天，默认 7 天。
- 备注：可选，建议最多 60 个字符，用于标识这一批；不需要提前知道收件人用户名。
- 固定说明“每个邀请码仅可注册一个普通账号。注册成功后自动登录。”
- 提交按钮按数量显示“生成 N 个邀请码”；无需在填写之后再加一轮无信息的确认。

批量生成全部成功或全部回滚。所有有效期按服务端创建时刻计算，不受管理员浏览器时区/时钟影响。

### 生成结果与复制

生成后同一抽屉变为结果状态，显示本批每个完整邀请码、有效期、单条复制及“复制全部”。复制全部每行一个代码，使用说明在复制区外独立显示，不把房间邀请混进去。复制成功只在剪贴板写入确实成功时提示；失败时选中文本方便手动复制。

完整邀请码仅本次生成响应显示，提示“请复制保存，关闭后无法再次查看完整邀请码”。首次关闭且尚未复制时提醒一次，用户仍可明确关闭。关闭/刷新不自动撤销有效代码；丢失代码可在历史记录撤销后重新生成。

不新增带邀请码的 URL、二维码、自动下载文件或分享服务；首版完全覆盖用户提出的“填写邀请码注册”。

若生成响应丢失，前端用本次 batch_id 查询历史确认是否生成，避免连点产生未知批次。相同 batch_id 重试不能再创建一批；若已经成功，返回批次已存在的错误码，由列表接口提供元数据，原码不可恢复。页面提示用户撤销丢失的未使用代码，再生成新批次。

### 撤销与状态

仅“未使用”有撤销按钮。确认文案“撤销后，此邀请码将无法用于注册。已创建的账号不受影响。”服务端成功后才更改状态；失败保留行内重试。后台不删除历史记录，不恢复已撤销/已过期代码。

状态优先级：已使用 > 已撤销 > 已过期 > 未使用。使用和撤销必须互斥；到期之后已使用仍显示已使用。历史展示使用者只对管理员开放，不构成完整用户管理。

管理员可能边看片边生成邀请码：桌面保留现有底部迷你播放器；抽屉和迷你播放器布局互不挡住按钮。窄屏抽屉打开时可以收起视频画面，仅保留播放实例和声音，关闭后恢复；不为抽屉重建 video、WS 或播放会话。

## 5. 视觉、动效与响应式

注册页顶部只放 RainSync 文字和“返回登录”。桌面居中面板约 850px，左侧窄步骤区，右侧表单；浅色面板 #F6EDE5 位于 #E5D1C1 画布。没有无功能的品牌插画或情绪文案。移动将步骤区改为顶部横向进度，表单单列，主操作满宽。

主按钮 #9E7867 配深色文字 #1A100B，正文 #30241F，次文 #6D5043；沿用 DESIGN 的边框、焦点和尺寸。16px 移动输入，至少 44px 点击区域，label 与错误关联，错误不是只靠颜色表达。

步骤切换 180–220ms 淡入和轻位移；不旋转翻牌、不反复晃动错误输入。验证成功立即允许继续。抽屉 280ms，复制反馈约 160ms。reduced-motion 下关闭位移，过渡 <=80ms。步骤切换后焦点移到下一步标题/首字段，错误后聚焦首个错误。

注册是匿名页面，不显示播放器；已登录管理页面则遵守原持续播放设计。360/390px 窄屏验证输入、软键盘、密码显示按钮及底部提交均可操作。

## 6. 拟新增接口契约（均未实现）

所有路径保持在现有 /api/v1 下。返回错误沿用现有 ErrorResponse/request_id 包装。

| 方法 / 路径 | 输入与权限 | 成功结果 |
|---|---|---|
| POST /admin/registration-invites | 管理员 Cookie + CSRF + Origin；batch_id、count、valid_days、note | 201；batch_id、items[id,code,code_suffix,expires_at]，完整 code 只在首次创建响应提供 |
| GET /admin/registration-invites | 管理员；status、cursor、limit、可选 batch_id | items 元数据、next_cursor、server_time；绝不返回 code/hash |
| DELETE /admin/registration-invites/{id} | 管理员 Cookie + CSRF + Origin | 撤销后的元数据；重复撤销幂等，已使用返回冲突 |
| POST /auth/registration-invites/validate | 匿名允许；Origin + application/json；code | 可用时返回 expires_at、server_time、code_suffix；不发登录会话、不锁定名额 |
| POST /auth/register | 匿名允许；Origin + application/json；code、username（登录账号）、display_name（可选昵称）、password | 201；{id,username,display_name,admin:false,csrf} 及现有 rainsync_session Cookie |
| GET /auth/me（扩展） | 已登录；原有接口增加 display_name | 保留旧字段，display_name 缺失资料时回退到 username |
| GET /users/me/profile | 本人 Cookie | {id,username,display_name,custom_display_name}；自定义昵称可为 null，区别于默认显示 |
| PATCH /users/me/profile | 本人 Cookie + CSRF + Origin；仅接受 display_name | 与 GET 相同的最新资料；username/admin/user_id 等修改字段一律拒绝 |

既有 POST /users 扩展可选 display_name，并复用新建账号校验。现有登录仍使用 username/password，绝不把昵称映射为登录凭据。个人资料 PATCH 只改昵称，不创建新登录会话或改变房间身份。
头像专项额外扩展身份/资料/聊天响应的 avatar_url、avatar_version，注册时默认null；头像经独立PUT/DELETE修改，不能通过昵称PATCH写入任意URL。上述身份示例省略的头像字段以该专项契约补全。

建议新增稳定错误码 REGISTRATION_INVITE_INVALID、USERNAME_TAKEN、ALREADY_AUTHENTICATED、REGISTRATION_INVITE_ALREADY_USED、REGISTRATION_BATCH_CONFLICT、REGISTRATION_BATCH_ALREADY_CREATED。前三者按匿名注册边界使用；已使用的精确错误仅管理撤销接口返回，匿名邀请错误仍统一。复用 INVALID_REQUEST、RATE_LIMITED、ORIGIN_REJECTED 等现有错误。错误文案和 TS 类型必须从 Rust 源正常生成，不能手改生成文件。

批次冲突：相同 batch_id、相同创建者与相同参数返回 409 REGISTRATION_BATCH_ALREADY_CREATED，沿用标准错误包装；不同创建者或参数返回冲突，不透露原批数据。前端以已知 batch_id 查询列表并展示“已生成，完整邀请码无法重新显示”，不当作普通失败自动换 batch_id 重发。

新增匿名入口不要求尚不存在的登录 CSRF token，但必须严格验证配置的 Origin、JSON 内容类型和大小限制；管理员写操作继续现有认证、CSRF 与 Origin 检查。已有有效会话调用 register 返回 ALREADY_AUTHENTICATED，不切换浏览器身份。成功响应和邀请码列表/生成响应均 no-store。

## 7. 数据、并发与实现边界

新增 registration_invite_batches：id、created_by、created_at、count、valid_days、note。新增 registration_invites：id、batch_id、code_hash UNIQUE、code_suffix、expires_at、used_by NULL、used_at NULL、revoked_at NULL、revoked_by NULL。通过 batch 关联创建者；约束保证 used_by/used_at 成对、used 与 revoked 互斥。索引覆盖批次、排序分页和到期筛选。

新增 user_profiles(user_id PRIMARY KEY REFERENCES users(id), display_name TEXT NOT NULL)。采用独立资料表，不改变 users/sessions 的列形状，避免破坏现有 INSERT INTO users VALUES(...) 和回滚版本。旧账号无需强制批量改名：查询时 LEFT JOIN + COALESCE，第一次修改昵称才 UPSERT；新账号填写昵称则在注册事务中创建资料行。清空昵称删除本人的自定义资料行，恢复回退值；不用一行空字符串覆盖默认值。username 永远保存登录账号，不用昵称覆盖。资料仅允许有效文本和约定长度，数据库约束与服务端校验对应；SQL 不拼接用户文本。

邀请码建议使用 160 位加密随机数，编码为不易混淆的 32 位大写 Base32 字符，加 RS 前缀并分组。接受粘贴时的空格/分隔符与小写，统一规范化后做带 registration 域标识的 SHA-256；数据库只存摘要和末 4 位。注册表与房间邀请表相互独立，不能互换 token。生成时随机碰撞由 UNIQUE 兜底。

注册顺序：字段/限流/邀请码粗检 → 有并发上限的 Argon2 哈希任务 → 开事务并锁定邀请码行 → 按锁定后的数据库实时时刻复查过期、撤销和已用 → 插入普通用户及可选昵称资料 → 标记 used_by/used_at → 插入登录会话 → 一起提交 → 发 Cookie。哈希不持有数据库锁，不在 async executor 上阻塞。不得信任请求中传来的 admin/角色或有效期。

用户名冲突、会话写入失败或任何事务失败都回滚用户与消费记录。两个用户同时提交同一码，至多一人成功。撤销和注册竞争同一行锁，先完成者决定结果；撤销不是事后删除账号。等待锁后必须重验有效期，不能仅使用事务开始时的 now()。

新增匿名接口必须在 Argon2 前限流，并限制同时计算数和队列/等待时间。新增独立的限流窗口记录（scope、key_hash、window_started、attempts）及清理规则，不复用按用户名计数的现有登录表。建议初始阈值：每个可信来源 IP 的校验 30 次/分钟、注册提交 10 次/10分钟，另设全站计算并发上限；实现时按部署资源调整并写入配置说明。429 给明确重试时间；多实例计数与有效期不能只依赖单进程内存。

真实客户端 IP 只能来自直接 peer 或可信反向代理的受控转发链，不直接信任任意 X-Forwarded-For。现有 Server 入口尚需接入 peer 信息/可信代理配置；设计 Plan 将其作为实现前置项。限流记录只保留必要摘要与窗口，不保存邀请码或密码。使用与撤销记录保留于业务表供管理员查询，不额外扩成完整审计平台。

## 8. 必须验证的结果

- 一次有效注册得到一个普通账号、正确昵称、一次消费和可用登录会话，自动进入 /rooms，未自动加入任何房间。
- 登录账号字符集、唯一且不可改；昵称可重名、中文/Emoji、修改与默认回退；密码 7/8 位边界、中文拒绝、英文空格保留，前后端一致。
- 存量账号/会话兼容，旧客户端继续读 username，新界面显示 display_name；昵称修改不改变权限或登录凭据。
- 同码并发、注册与撤销并发、恰好到期、用户名占用、密码错误及事务中断均有数据库级验证。
- 验证邀请码不消耗；失效码、房间邀请 token、伪造 admin 字段不能绕过注册规则。
- 批量生成 1/50 边界、非法数量/有效期、响应丢失和重复 batch_id 可恢复，列表不泄露原码或摘要。
- 注册超时不会自动重发；注册成功但响应丢失可通过现有登录恢复，不能以再次注册试探结果。
- 匿名/普通用户无法列出或生成代码；管理员写操作仍检查 CSRF；Origin 和可信代理限制可测试。
- 注册页和管理页覆盖键盘、窄屏、减少动态效果、空态、失败态、复制失败；在管理区生成/撤销时保持播放实例。

以上均是将来验收要求。本轮没有运行 Server、迁移数据库、创建账号或测试注册功能。
