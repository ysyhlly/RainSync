# 播放和媒体队列容量

Server 读取两个正整数配置，范围为 1–10000；非法、空字符串或非整数使启动失败。

| 配置 | 默认 | 计数范围 |
|---|---:|---|
| PLAYBACK_SESSION_LIMIT | 2 | 每用户未停止且未过期的会话，以及租约有效的待完成准备；相同 session_id 去重 |
| MEDIA_QUEUE_LIMIT | 20 | 全局 queued/running 媒体任务，且关联播放会话未停止、未过期 |

每用户配额继续通过 users 行锁串行决策。同键回放不新增名额。降低配置不强行停止现有会话，只阻止超额的新准备；需要保留原先八路行为的部署可显式配置 `PLAYBACK_SESSION_LIMIT=8`。示例环境和 Compose 均已提供配置。

本地生成任务在播放会话和方案提交的同一事务内入队。入队函数先取得 PostgreSQL 事务级 advisory lock 72614932，然后统计容量、插入任务；锁保持到提交/回滚，防止不同用户并发越界。探测及上游网络操作在这笔事务之前完成。数据库插入工具和运维脚本不能绕过此入队函数，否则不受应用层容量保证。

队列满返回 HTTP 503 / `MEDIA_QUEUE_FULL`，可重试；该次事务不留下新的活跃会话或任务。按 key 的失败收尾仍会记录失败，同 key 重试沿用原有三次准备上限。网页已识别此码并有限重试。直放及直接代理上游的方案不消耗本地媒体任务名额，仍受每用户会话上限约束。

这里的队列上限包含运行中的有效任务，不是 FFmpeg 并发配置。取消或过期任务停止计数后，其子进程可能仍在被回收；实际写入继续受 Worker 租约、进程监督和缓存预算约束，不能把 20 理解为同时允许 20 条转码。探测并发也没有被此队列设置代替。

migration 0016 新增数据库轮次记录。每次领取先取得短事务级调度锁，再优先选择最久未获分配的用户；尚无分配记录的用户先参与，用户内按任务创建时间及 ID 排序。锁住的任务使用 SKIP LOCKED 跳过；未到重试时间、取消、过期或已耗尽重试次数的任务不参与。轮次更新、任务领取和新 attempt 的产物记录同事务提交，失败全部回滚。轮次由数据库保存，不依赖 Worker 内存；无用户的历史/系统任务合并为一个调度桶。

这种公平性是任务领取机会的轮转，不是 CPU 时间平均分配，也不抢占已经运行的长任务。一个 Worker 仍须等当前编码结束或回收后才领取下一个任务。持续直放/转码容量测量、实际多设备和负载验收仍待推进，不能仅凭计数和轮次测试公布吞吐能力。升级时先完成迁移，再启动使用新领取逻辑的 Worker；旧 Worker 仍按 FIFO 领取，混合版本期间不能承诺公平顺序。

隔离数据库测试覆盖并发最后一个名额、运行任务计数、失败事务的会话回滚及撤销后释放；API 集成覆盖满队列错误契约、直放可用、没有孤立活跃会话或任务，以及容量恢复后的同键重试。既有每用户并发回归显式使用配置值 8，默认值 2 和配置合法性由单元测试检查。

公平调度的独立数据库例子覆盖用户 A 积压多条时与 B 交替、用户内次序、独立连接读取持久轮次、并发领取、产物插入失败回滚轮次、锁竞争和重试退避。这里的独立连接验证不等于完整机器重启验收。
