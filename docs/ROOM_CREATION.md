# 房间创建与安全重试

`POST /api/v1/rooms` 请求体为 `{ "name": "电影夜" }`。已登录、Origin 和 CSRF 校验仍然必需。Web 在提交前生成 UUID 请求键，通过 `Idempotency-Key` 请求头发送；同一用户、同一名称的失败重试会沿用该键。

服务端按 **账户 ID + 请求键** 持久保存原始名称与创建结果。请求键为 1–128 个 ASCII 字符，只允许字母、数字、`.`、`_`、`:`、`-`，不允许重复请求头。同键同名称的重试与并发请求返回相同 `{ "id": "…" }`；同键改名返回 HTTP 409，原房间和原结果不变。名称按原始字符串比较，空格也属于请求内容。请求体仅接受 `name`，未知字段返回 HTTP 422。

去重记录、房间、创建者成员资格和初始快照在同一个 PostgreSQL 事务内提交；失败时全部回滚。数据库唯一键协调多个 Server 进程，重启后仍能重放。创建事务会锁定账户和精确登录会话，并在提交前按实际时钟复检会话有效期；排队期间登录到期会拒绝并回滚。结果重放只确认原创建结果，不恢复已撤销的成员资格或重新开放房间。

Web 在同一标签页的 `sessionStorage` 中保存未确认的请求键，页面刷新后可用原名称重试。确认成功后清除该键，下次明确创建使用新键；改名和切换账户使用不同键。浏览器禁止存储时，当前页面仍保留键，但刷新后的恢复不可用。无法确认结果时，先用原名称重试；改名会视作新创建操作。

旧客户端可以不提供请求键，保留每次请求创建新房间的行为；这类客户端必须先升级才有安全重试保证。安全重试也要求 Server 已升级并应用迁移 `0079`，旧 Server 不处理该请求头。注册邀请码与房间创建请求键没有关联。

去重记录随账户清除；房间关闭或物理删除不会清除记录，因此原请求仍返回原 ID，不会新建替代房间。当前没有按时间自动淘汰记录；引入清理策略前必须先声明有限重试窗口，不能静默重用已消费的键。

验证：`node tests/room-creation-idempotency.mjs` 使用隔离 PostgreSQL 和当前 Server 二进制验证并发、丢失应答、载荷冲突、事务回滚、重启重放、用户隔离、会话到期及旧客户端兼容。需要配置现有测试 fixture 要求的 `RAINSYNC_ARTIFACT_DIR` 与 `CARGO_TARGET_DIR`。
